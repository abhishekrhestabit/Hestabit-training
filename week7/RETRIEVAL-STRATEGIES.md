# Retrieval Strategies — Day 2

## Why Basic Semantic Search Is Not Enough

A single vector similarity search works well for paraphrase-style queries but fails when the user uses exact keywords, acronyms, or domain-specific terms that don't appear in the training vocabulary of the embedding model. It also tends to return very similar chunks because dense vectors cluster nearby documents together, reducing the diversity of the retrieved context. Day 2 addresses these weaknesses by combining multiple retrieval strategies.

---

## Hybrid Search: BM25 + Semantic Embeddings

BM25 is a classical keyword-based ranking algorithm. It scores documents by term frequency and inverse document frequency, meaning it rewards chunks that contain the exact words from the query and penalises very common words. It has no concept of meaning — only of word match.

Semantic search using dense embeddings does the opposite. It understands meaning and paraphrase but can miss exact keyword matches.

Combining both with equal weights (50/50 ensemble) gives the best of both worlds. A query like "EBITDA margin Q3 2024" will score highly on BM25 because of the exact terms, while a conceptual query like "explain profitability trends" will score highly on the semantic side. The ensemble retriever merges and deduplicates the two ranked lists.

---

## Max Marginal Relevance (MMR)

Standard similarity search returns the top-k chunks most similar to the query, but these chunks often overlap heavily in content. MMR is a reranking objective that balances relevance against diversity. It iteratively selects the next chunk that is both relevant to the query and as different as possible from the chunks already selected. This reduces redundancy in the context window and exposes the LLM to a broader range of information.

In this system MMR is applied on the semantic vector retriever side, with `fetch_k=20` (candidates) narrowed to the final `k` using the MMR objective.

---

## Cross-Encoder Reranking

The hybrid retriever produces a broad candidate set (up to 10 chunks). A cross-encoder model then re-scores every candidate against the query in a single forward pass that considers both texts together — unlike bi-encoders that embed query and document independently.

The model used is `cross-encoder/ms-marco-MiniLM-L-6-v2`, trained on the MS MARCO passage retrieval benchmark. It produces a relevance score per (query, chunk) pair. The top-n chunks by score are returned as the final context.

Cross-encoder reranking consistently improves precision at the cost of slightly higher latency, which is acceptable since it only processes the small candidate set rather than the entire corpus.

---

## Chunk Deduplication

After the hybrid retrieval step, the same chunk can appear in both the BM25 and semantic results. Deduplication removes exact content duplicates before reranking. This prevents the same passage from occupying multiple slots in the final context window, which would waste tokens and bias the LLM toward that passage.

---

## Metadata Filtering

Every chunk stored in FAISS carries metadata tags set at ingest time (source, page, file_type, tag). The hybrid retriever supports post-retrieval metadata filtering — for example, restricting results to a specific year or document type. This is useful in enterprise settings where documents span multiple years, departments, or policy versions and you need to scope the context.

---

## Traceable Context

Each final chunk passed to the LLM is annotated with its source file, page number, and file type. This traceability serves two purposes. First, it allows the LLM to cite its sources in the answer. Second, it allows engineers to audit why a particular answer was generated by inspecting which chunks were used, making the system debuggable and trustworthy.

---

## Pipeline Flow

The full Day 2 pipeline in order is:

- Hybrid retrieval fetches a wide candidate set using BM25 + MMR semantic search in parallel.
- Metadata filters are applied if provided.
- Deduplication removes exact duplicate chunks.
- Cross-encoder reranking rescores the remaining candidates and returns the top-n.
- The context builder formats the final chunks with source annotations for the LLM.

---

## Key Principles

- **Fetch wide, rank narrow** — retrieve more candidates than needed (top 10), then filter down to the best (top 5 after reranking). This avoids discarding relevant chunks too early.
- **Never trust a single retrieval signal** — keyword and semantic retrievers each have blind spots. Combining them is more robust than either alone.
- **Token budget matters** — the context window of an LLM is finite. Deduplication and reranking ensure the budget is spent on the most useful, diverse chunks rather than repetitive content.
- **Traceability is not optional** — in enterprise use cases, every answer must be auditable. Attaching source metadata to each chunk enables this.
